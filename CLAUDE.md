# CLAUDE.md

Este arquivo fornece orientações ao Claude Code (claude.ai/code) ao trabalhar com código neste repositório.

## Visão geral do projeto

API de Gestão e Controle de Projetos da Pascom Santuário N. Sra. de Fátima — uma API REST em Spring Boot 3.2 / Java 17 para gerenciar o fluxo de conteúdo de uma equipe de comunicação paroquial: ideias de conteúdo, um quadro de produção estilo Kanban ("cartões") e escala de voluntários para eventos.

O repositório também guarda o front-end em [src/main/resources/static/index.html](src/main/resources/static/index.html) — um app single-file (HTML/CSS/JS puro, sem build), servido automaticamente pelo próprio Spring Boot na raiz (`/`). É por isso que fica dentro de `resources/static`: não é um projeto à parte, é a UI desse mesmo backend. As chamadas de API usam `API_BASE='/api'` (caminho relativo), então funcionam sem alteração tanto local quanto em produção — sobe o backend (`mvn spring-boot:run`) e acessa `http://localhost:8080/`, sem precisar de nenhum servidor separado pro front.

## Comandos



```bash

```


Atualmente não há classes de teste em `src/test/java` — `mvn test` vai reportar nenhum teste executado.

A aplicação sobe na porta 8080. O console do H2 está disponível em `/h2-console` (URL JDBC `jdbc:h2:file:./data/pascomdb`, usuário `sa`, sem senha), pois `spring.h2.console.enabled=true` em [application.yml](src/main/resources/application.yml).

## Arquitetura

Estrutura em camadas padrão do Spring MVC sob `br.org.pascom`:

- `controller/` — `@RestController`s, um por agregado (`Usuario`, `Evento`, `Cartao`, `Ideia`), todos montados sob `/api/**`. Controllers apenas traduzem HTTP <-> DTO e delegam para os services; nenhuma regra de negócio aqui.
- `service/` — regras de negócio e orquestração. Os services dependem dos repositories diretamente (sem camada separada de mapper); a conversão DTO <-> entidade acontece via métodos estáticos de fábrica nos próprios DTOs (ex.: `UsuarioResponseDTO.from(usuario)`) ou inline no service.
- `repository/` — interfaces `JpaRepository` simples, sem lógica de query customizada além de queries derivadas estilo `findByEmail`.
- `model/` — entidades JPA (Lombok `@Getter/@Setter/@Builder`), além de `model/enums/` para `Role`, `Etapa`, `Formato`, `SlotTipo`.
- `dto/` — `record`s Java para requests/responses, com anotações de validação (`jakarta.validation`).
- `config/` — `WebConfig` (CORS global em `/api/**`, atualmente `allowedOriginPatterns("*")`), `SecurityConfig`/`SecurityFilter` (autenticação stateless via JWT, ver abaixo) e `ApiExceptionHandler` (`@RestControllerAdvice` que traduz `IllegalStateException`/`IllegalArgumentException`/erros de validação/`AuthenticationException` em corpos JSON `400`/`401`). Em `SecurityConfig`, só `/api/**` exige autenticação (exceto cadastro/login) — o front-end estático é sempre público, já que a autenticação de verdade acontece nas chamadas de API que ele faz, não no carregamento da página.

### Autenticação

A API usa **JWT stateless** via Spring Security. `POST /api/usuarios/login` autentica com `AuthenticationManager` e devolve um `LoginResponseDTO{token, usuario}`; o front deve enviar esse token em todas as demais chamadas via header `Authorization: Bearer <token>`. `SecurityFilter` ([SecurityFilter.java](src/main/java/br/org/pascom/config/SecurityFilter.java)) lê e valida o token em cada request e popula o `SecurityContext`; `TokenService` ([TokenService.java](src/main/java/br/org/pascom/service/TokenService.java)) gera/valida o JWT (segredo em `api.security.token.secret`, sobrescrevível pela env var `JWT_SECRET` — **troque o valor padrão antes de produção**). O login vale `api.security.token.validade-horas` (env `JWT_VALIDADE_HORAS`, padrão 168 = 7 dias). Como o token é stateless e assinado com `JWT_SECRET`, **deploy não desloga ninguém** — não troque o `JWT_SECRET` à toa, isso desloga todo mundo. Apenas `POST /api/usuarios/cadastro`, `POST /api/usuarios/login`, `POST /api/usuarios/esqueci-senha`, `POST /api/usuarios/redefinir-senha` e `POST /api/usuarios/google` são públicos; todo o resto de `/api/**` exige token válido.

- **Recuperação de senha**: `POST /api/usuarios/esqueci-senha {email}` gera um token (`Usuario.resetSenhaToken`, válido 1h) e manda um e-mail com o link `/?resetToken=...` via `EmailService` — sempre responde `200`, mesmo se o e-mail não existir (evita enumerar contas). `POST /api/usuarios/redefinir-senha {token, novaSenha}` troca a senha e limpa o token. O front detecta `?resetToken=` na URL (`init()`) e mostra a tela de nova senha. **Plano B** (o remetente padrão `onboarding@resend.dev` só entrega pro dono da conta Resend, então sem domínio verificado em `RESEND_FROM` o e-mail não chega pra ninguém mais): `POST /api/usuarios/{id}/link-redefinicao` (só Coordenação Geral) gera o mesmo token, válido 24h, e devolve o link; no front, botão "Gerar link de nova senha" em cada pessoa da aba Equipe, com a mensagem pronta pra copiar ou abrir no WhatsApp. Depois do cadastro o front já faz login sozinho (não pede e-mail e senha de novo).
- **Login/cadastro com Google**: `POST /api/usuarios/google {idToken, role?, setor?, funcao?}` — `GoogleTokenService` valida o ID token direto no endpoint público `oauth2.googleapis.com/tokeninfo` (confere `aud` contra `api.security.google.client-id` / env var `GOOGLE_CLIENT_ID`, e `email_verified`). Se já existe um `Usuario` com aquele e-mail, loga direto; se não existe e `role` veio `null`, devolve `{precisaCompletarCadastro:true, nome, email}` pro front pedir papel+setor antes de chamar o endpoint de novo (dessa vez com `role`/`setor` preenchidos, criando a conta com senha aleatória — essas contas nunca logam por senha, só por Google, a menos que peçam redefinição). O front carrega o script `accounts.google.com/gsi/client` e usa `google.accounts.id` (Google Identity Services); o Client ID **não é secreto** e fica hardcoded em `index.html` (constante `GOOGLE_CLIENT_ID`) além de configurado no backend.

Nos controllers, o usuário autenticado é injetado via `@AuthenticationPrincipal Usuario` — os métodos de service que representam "quem está fazendo a ação" (`moverEtapa`, `adicionarComentario`, `alterarRole`, `inscreverVoluntario`, criar/votar `Ideia`) recebem esse `Usuario` diretamente, e não mais um ID enviado pelo cliente. Respostas de erro de autenticação (401) e autorização (403) seguem o mesmo formato `{"erro": "..."}` do restante da API, configurado em `SecurityConfig.exceptionHandling`.

### Modelo de domínio

- **Usuario**: um membro da equipe; implementa `UserDetails` do Spring Security (o `Role` vira a authority `ROLE_<role>`). Reflete a estrutura real da pastoral: `Role` é `COORDENADOR_GERAL` (coordena a pastoral inteira, todos os setores — não tem `Setor`, o campo fica `null`), `COORDENADOR` (coordena um `Setor` específico) ou `VOLUNTARIO` (também pertence a um `Setor`). `Setor` é `REDES_SOCIAIS`, `JOVENS`, `DATASHOW` ou `TRANSMISSOES_VIDEOS`. A própria pessoa escolhe papel + setor no cadastro (`POST /api/usuarios/cadastro`, validado em `UsuarioService.cadastrar`: setor é obrigatório pra quem não é `COORDENADOR_GERAL`) — não existe mais a regra antiga de "primeiro usuário vira admin automaticamente". Em compensação, **só pode existir um `COORDENADOR_GERAL` no sistema**: `cadastrar` bloqueia (`IllegalStateException`) qualquer tentativa de cadastro com esse papel se `usuarioRepository.existsByRole(COORDENADOR_GERAL)` já for verdadeiro — é a primeira pessoa a escolher esse papel que "ocupa a vaga", ninguém mais consegue depois. `COORDENADOR` (de setor) e `VOLUNTARIO` continuam livres pra qualquer um se cadastrar, sem limite. Só `COORDENADOR_GERAL` pode alterar a função de outro usuário ([UsuarioService.java](src/main/java/br/org/pascom/service/UsuarioService.java)): `PATCH /api/usuarios/{id}/papel {role, setor}` (`alterarPapel`; ninguém muda o próprio papel, só pode existir um Coordenador Geral, e o novo setor principal sai dos extras). No front é o botão "Gerenciar" em cada pessoa da Equipe e do Time da Pascom (só pra Coordenação Geral), que também gera o link de nova senha. O `PATCH /{id}/role` antigo continua, mas não mexe no setor. No mesmo "Gerenciar" fica a marcação **Gestor(a) de escalas** (`Usuario.gestorEscalas`, coluna `gestor_escalas`): dá poderes de Coordenação Geral **só nas escalas** de todos os setores (`gereTodasAsEscalas()`, `coordenaEscalaDoSetor()`, `podeMontarEscalas()` no backend; `gereEscalas()`/`coordenaEscala()` no front) — ver montagem e candidatos, escalar/trocar/tirar, editar funções, publicar, histórico, evento extra, excluir/restaurar evento, gerar missas do mês. Não muda papel de ninguém nem gera link de senha. Senhas são hasheadas com BCrypt e marcadas com `@JsonIgnore`.
  - **Setores extras** (`Usuario.setoresExtras`, tabela `tb_usuario_setores_extras`, `EAGER` porque o usuário é carregado no `SecurityFilter` fora de sessão do Hibernate): além do setor principal do cadastro, a pessoa marca no próprio perfil (`PUT /api/usuarios/me {nome, funcao, disponibilidade, setoresExtras}`) outros setores em que também serve. Isso só dá **participação na equipe**, não poder de coordenação — coordenador continua coordenando só o setor principal. `Usuario.fazParteDoSetor(s)` = setor principal, extra, ou `COORDENADOR_GERAL` (a flag `admin` não conta aqui: dá poderes, mas não coloca a pessoa em todas as equipes). Usado em `desinscreverVoluntario` ("pessoas da sua equipe" inclui quem entrou como extra) e, no front, em `pertenceSetor(m,s)`.
  - **Foto de perfil**: fica em `FotoUsuario` (`tb_fotos_usuario`, id = id do usuário), separada de `tb_usuarios` de propósito pra não ser carregada a cada request autenticado; `Usuario.fotoAtualizadaEm` vira `fotoVersao` (epoch ms) no `UsuarioResponseDTO`. `PUT /api/usuarios/me/foto` (corpo = bytes da imagem, até 1 MB, tipo conferido pelos bytes — JPEG/PNG/WebP), `DELETE /api/usuarios/me/foto`, `GET /api/usuarios/{id}/foto?v=<fotoVersao>` (exige login, cache privado de 30 dias — a versão na URL invalida). O front reduz no navegador pra um quadrado de 400px JPEG antes de enviar (`reduzirFoto`) e, como `<img src>` não manda o header `Authorization`, baixa cada foto com `fetch` e usa um `blob:` URL (`fotoUrl`/`carregarFoto`, troca as iniciais nos avatares já renderizados via `[data-av]`).
  - **Flag `admin`** (coluna `admin_sistema`): dá poderes de Coordenador Geral a quem tiver, independente do papel (`Usuario.temPoderesDeCoordenadorGeral()` = `COORDENADOR_GERAL` **ou** `admin`). Substitui o e-mail da desenvolvedora que antes ficava fixo no código — **não colocar e-mail fixo no código de novo**. É ligada na inicialização a partir da env var `ADMIN_EMAILS` (separados por vírgula, ver `InicializacaoDados`) e nunca pela API. O front recebe `poderesCoordenadorGeral` no `UsuarioResponseDTO` em vez de comparar e-mail. Helpers de permissão em `Usuario`: `isCoordenacao()` (coordenador de setor ou geral), `coordenaSetor(Setor)` (geral, ou coordenador daquele setor).
  - **E-mails sempre minúsculos e sem espaços** (`Usuario.normalizarEmail`) no cadastro, login, Google, esqueci-senha, `AutenticacaoService` e `SecurityFilter`. `InicializacaoDados` normaliza na subida os e-mails antigos (pula e loga se duas contas só diferirem por maiúsculas).
- **Ideia**: uma ideia de conteúdo, pertence a um `Setor` (igual `Cartao`, ver abaixo). Qualquer um pode criar e votar (alternar voto) em ideias. Uma ideia pode ser "adotada" (`adotada = true`), o que a converte 1:1 em um novo `Cartao` no mesmo setor, na etapa `IDEIA`, via `IdeiaService.transformarEmCartao` — bloqueado com `IllegalStateException` se a ideia já tiver sido adotada antes (evita cartão duplicado).
- **Cartao**: um cartão de produção que percorre o pipeline de `Etapa`: `IDEIA -> ROTEIRO -> GRAVACAO -> EDICAO -> REVISAO -> AGENDADO -> PUBLICADO`. Qualquer usuário autenticado pode criar cartões, avançar etapas e agendar/publicar — não há checagem de papel em `CartaoService.moverEtapa`. A única trava é de qualidade, não de permissão: avançar para `AGENDADO` ou `PUBLICADO` exige que o `Checklist` embutido no cartão (5 flags booleanas de segurança/revisão) esteja totalmente completo (`Checklist.isCompleto()`). Uma dessas flags, `doutrinaConferida`, tem uma trava a mais: `CartaoService.aplicarChecklist` bloqueia (`IllegalStateException`) a transição de "não conferida" pra "conferida" quando quem está salvando não é coordenador (`Usuario.podeConferirDoutrina()`) — reenviar o mesmo valor que já estava salvo continua permitido, só a transição falsa→verdadeira por quem não pode é que é barrada; isso existe porque o front só desabilitava o checkbox visualmente, o que não impedia uma chamada direta à API. Cada `Cartao` pertence a um `Setor` (campo nullable no banco, mas obrigatório via `@NotNull` no `CartaoRequestDTO` — nullable no schema pra nunca travar uma migração em produção, ver "Navegação por setor" abaixo).
- **Evento** / **SlotEscala**: um evento com uma lista de "slots" (funções) de voluntários. **O evento não pertence a um setor** — é compartilhado entre toda a pastoral (ex.: um bazar pode envolver várias equipes) — mas **cada slot tem um `setor`** (null = função geral); `tipo` (`SlotTipo`) agora é opcional, o `rotulo` é o que vale. Qualquer coordenador (`isCoordenacao()`) pode criar evento extra com escala (`EventoService.criar`) e adicionar funções (`adicionarSlot`); coordenador de setor só cria funções do **próprio** setor (o setor enviado é ignorado), o Coordenador Geral escolhe. **Escala com candidatura e publicação (sigilo)**: nas funções de setor, ninguém se escala direto. O voluntário toca em **"Quero servir"** (`POST/DELETE /api/eventos/{id}/slots/{slotId}/candidatura`, `CandidaturaEscala`), a coordenação do setor (ou a Geral) vê os candidatos e põe/troca a pessoa (`POST .../escalar {usuarioId}`, `EventoService.escalar`: a pessoa tem que ser do setor e não pode estar em outra função da mesma missa) e, quando a escala do mês está pronta, **publica** (`POST /api/escalas/publicar?mes=AAAA-MM&setor=X`, `PublicacaoEscala` por mês+setor; `despublicar` volta pra montagem). Enquanto não publicada, **o servidor esconde quem foi escalado** de quem não coordena o setor (`SlotEscalaDTO.oculto` = true e `voluntarioId/Nome` null — inclusive a própria pessoa), e `candidatos` só vai pra coordenação; isso vale pra `/api/eventos`, escala completa e PDF (que mostra "em montagem"). Por isso todo método que devolve `EventoDTO` recebe quem está vendo (`toDTO(evento, viewer)`/`Visao`). `inscreverVoluntario` checa "é por candidatura" **antes** de "vaga preenchida", pra não vazar que a função em montagem já tem alguém. Funções gerais (sem setor) continuam com "Eu vou" direto e sem montagem. **Avisos e histórico**: `AvisoService`/`Aviso` (`GET /api/avisos`, `POST /api/avisos/lidos`; sininho no topo, recarrega ao voltar pra aba e a cada 2 min) avisa a pessoa quando é escalada, trocada, tirada ou tem a função removida — **só se a escala daquele mês/setor já estiver publicada** (em montagem é sigiloso); ao publicar (manual ou automática), cada escalado recebe um aviso com as funções dele no mês. `AlteracaoEscala` (`GET /api/escalas/historico?setor=X`, só coordenação do setor/Geral) guarda em texto quem escalou, trocou, tirou, publicou, voltou pra montagem e renomeou/removeu/adicionou função; no front, "Histórico de alterações" no fim da escala do setor.

**Ciclo mensal**: o mês atual e o próximo sempre existem (geração do dia 1). O **mês que vem** fica em montagem durante o mês inteiro pra candidaturas; **a partir do dia 25** quem coordena vê no Painel e nas Escalas o aviso "Falta publicar a escala de <mês>" (`lembretePublicacaoHtml`, só front); **no dia 1, às 6h** (e na subida da aplicação, caso o servidor estivesse fora no dia 1), `EventoService.publicarMesQueChegou` publica sozinho o mês atual de todo setor que ninguém publicou. **O mês que chegou fica fechado** pra equipe, **a partir de novembro/2026** (`PRIMEIRO_MES_COM_FECHAMENTO`, no `EventoService` e no front: outubro/2026, quando o sistema começou, fica aberto até o fim) (`mesFechado`/`exigirMesAberto`): sem candidatura, desistência, "Eu vou" nem sair sozinho ("fale com a coordenação"); a coordenação continua escalando/trocando/tirando pra cobrir imprevistos, e não dá mais pra voltar esse mês pra montagem. Remover uma função apaga as candidaturas dela antes (FK).

Antes disso, voluntários se auto-inscreviam (`inscreverVoluntario`, hoje só pras funções gerais) **só nas vagas dos setores deles** (setor principal ou extras do perfil, `Usuario.fazParteDoSetor`; função geral, sem setor, é aberta a todos; Coordenação Geral faz parte de todos) — no front, a vaga de outro setor mostra "Só pra <setor>" no lugar do "Eu vou" e a aba avisa com atalho pro perfil. A gravação é um `UPDATE ... WHERE voluntario IS NULL` atômico (`SlotEscalaRepository.ocuparSeLivre`): com várias pessoas clicando "Eu vou" na mesma vaga ao mesmo tempo, só uma ganha e as outras recebem "Alguém acabou de pegar essa vaga" (antes, "conferir e depois gravar" deixava todas receberem sucesso e a última apagava as outras — reproduzido com 40 usuários simultâneos). O front recarrega a escala quando isso acontece e sempre que a pessoa volta pra aba (`recarregarEventos`). **Tirar alguém da escala** (`desinscreverVoluntario`) só pode: a própria pessoa, o Coordenador Geral, ou o `COORDENADOR` do mesmo setor da pessoa escalada. Excluir/restaurar evento continua só Coordenador Geral. Ambos validam que o `slotId` realmente pertence ao `eventoId` informado; `inscreverVoluntario` também bloqueia se o slot já tiver outro voluntário (evita sobrescrever silenciosamente quem já estava escalado) ou se o próprio voluntário já estiver em outro slot do mesmo evento.
- **Comentario**: comentários em thread anexados a um `Cartao`, de autoria de um `Usuario`. Sempre salvo via `ComentarioRepository` diretamente (não por cascade do `Cartao`), pra garantir que o `id` (IDENTITY) já volte preenchido na resposta.
- **ContaInstagram** / **PostagemInstagram** / **MetricaInstagram** / **MetaInstagram**: integração com a Instagram Graph API (leitura automática de posts, histórico de métricas e metas de crescimento) — ver seção própria abaixo.
- **MissaDatashow** / **Transmissao**: fluxos próprios dos setores Datashow e Transmissões/Vídeos — ver "Fluxos por setor" abaixo.

### Navegação por setor

O front-end tem um seletor de "espaço" na barra lateral (`setorSwitchHtml()`, estado `currentSetor`/`setorMenuOpen` em `index.html`) que funciona como um workspace switcher (estilo Notion/Slack): troca entre os 4 setores da pastoral e filtra Painel, Produção (quadro Kanban), Calendário e Ideias pra mostrar só o conteúdo daquele setor — cada espaço é totalmente isolado (cartões/ideias de um setor nunca aparecem em outro). `Equipe` tem duas abas (`equipeAba`): **"Equipe de <setor>"** mostra só quem faz parte do `currentSetor` (setor principal ou extra), a coordenação do setor e a Coordenação Geral, com aviso + atalho pro perfil quando a própria pessoa ainda não faz parte; **"Time da Pascom"** (`viewTime`) mostra todo mundo agrupado por setor, com fotos, filtro por setor e busca (quem está em mais de um setor aparece em cada um). O Painel tem um atalho com as fotos do time (`timePainelHtml`). **Meu perfil** (`viewPerfil`, `hidden:true` em `VIEWS`, fora do menu) abre pelo cartão com o nome no rodapé da barra lateral. Ao logar, `currentSetor` começa no setor da própria pessoa (`me().setor`), ou `redes_sociais` para o `COORDENADOR_GERAL`. Criar um cartão/ideia sempre usa o `currentSetor` do momento (`cartaoToApi`/`addIdea`); a API filtra por setor tanto no carregamento (client-side, via `visibleCards()`/`visibleIdeas()`) quanto opcionalmente no backend (`GET /api/cartoes?setor=X` e `GET /api/ideias?setor=X`, ainda não usados pelo front, que prefere carregar tudo uma vez e filtrar localmente pra trocar de espaço instantaneamente sem round-trip).

**Views por setor** (`VIEWS_POR_SETOR`/`viewDisponivel` em `index.html`): Produção, Dashboard e Ideias só existem em **Redes sociais e Jovens** (`SETORES_CONTEUDO`, quem produz conteúdo); **Datashow e Transmissões** trabalham pela escala, então não têm essas telas (nem o "+ Novo cartão"), o Painel deles é `viewPainelEscala` (próxima missa do setor, suas escalas, vagas abertas) e a Lixeira só mostra escalas. Transmissões tem a aba **Guia** (roteiro de câmeras e passo a passo pra ir ao vivo). Se a view atual não existir no setor escolhido, `render()` volta pro Painel. O último espaço aberto fica salvo no aparelho (`localStorage` `pascom-fatima-setor`, limpo no logout). Os quadros próprios de Datashow (`MissaDatashow`) e Transmissões (`Transmissao`) continuam no backend, só não aparecem mais no front.

**Celular (`≤860px`)**: barra do topo (`#mbar`, `renderMobileBars`) com o espaço atual (toque abre a gaveta já no seletor de espaço, `abrirTrocaSetor`) e a foto da pessoa (perfil); **barra de abas embaixo** (`#tabbar`) com as 4 telas principais do setor (`abasPrincipais()`) + "Mais", que abre a gaveta lateral com o menu completo (`.side.open`, fecha ao navegar, no backdrop ou com Esc). A ação principal da tela ("+ Novo cartão") vira botão flutuante acima das abas; janelas (`.modal`) abrem como painel de baixo pra cima, com o corpo rolando e o rodapé (Salvar) sempre visível; campos com fonte 16px (evita o zoom automático do iPhone); abas/filtros rolam de lado em vez de quebrar linha; o quadro Kanban desliza uma coluna por vez (`scroll-snap`). O Painel de todos os setores mostra "Suas próximas escalas" primeiro. Na aba Escalas, filtros Todas / Com vaga / Minhas (`escalaFiltro`), explicação recolhida em "Como funciona a escala" e o PDF numa caixa no fim. Não voltar a pôr a nav como fileira de ícones nem deixar a navegação só no hambúrguer.

### Fluxos por setor (Datashow e Transmissões)

Dois setores têm quadro Kanban próprio, no lugar do quadro de cartões (`viewQuadro()` escolhe por `currentSetor`). Ambos são abertos a qualquer usuário autenticado pra criar/editar/mover etapa, e usam **exclusão definitiva** (ainda sem lixeira) — por isso **excluir** exige `coordenaSetor(DATASHOW)` / `coordenaSetor(TRANSMISSOES_VIDEOS)` (coordenação do setor ou Coordenador Geral), assim como o disparo manual de `POST /api/transmissoes/gerar-mes`.

- **Datashow** (`MissaDatashow`, `/api/datashow/missas`): uma missa passa por `EtapaDatashow` = `AGUARDANDO_MUSICAS → CONFERINDO_MOMENTOS → MONTADO → PASSADO` (esperar a lista de músicas da pastoral da música, conferir os momentos com as pastorais, montar, passar na celebração). Tem dois responsáveis distintos — `responsavelMontagem` (por semana) e `responsavelPassar` (por missa) — além de `listaMusicas` e `avisosOutrasPastorais`.
- **Transmissões** (`Transmissao`, `/api/transmissoes`): `EtapaTransmissao` = `PLANEJANDO → CAPA_E_LINK_PRONTOS → TRANSMITIDO`, com `TipoTransmissao` (`MISSA_DOMINICAL`, `MISSA_SOLENE`, `BENCAO_SANTISSIMO`, `OUTRA`), tema litúrgico, link e capa. `POST /api/transmissoes/gerar-mes` (e um `@Scheduled` no dia 1 de cada mês, 6h) cria sem duplicar a "Missa das 10h" de cada domingo. No front há uma aba **Guia** com o roteiro de câmeras por momento da missa e o passo a passo pra ir ao vivo (YouTube Studio + Prism Live Studio).
- **Escalas** seguem o mesmo padrão de geração automática: `EventoService.gerarEscalasDoMes` (chamado por `garantirEscalasDoMesAtualEProximo`, que roda no `@Scheduled` do dia 1, 6h de Brasília, **e também na subida da aplicação** via `InicializacaoDados`, caso o servidor estivesse fora do ar no dia 1) cria, pro mês atual e o próximo, as missas de `MISSAS_AUTOMATICAS`, cada uma com as funções padrão e **sem ninguém escalado** — todo mês começa uma escala nova, limpa:
  - **Missa das 10h de todo domingo**: Redes sociais = Foto/Vídeo/Stories ao vivo; Transmissões = Câmera 1/2/3 + Corte da transmissão + Auxiliar de corte; Datashow = Datashow (sempre uma pessoa só). Jovens não tem padrão.
  - **Missas das 8h e das 18h30 de todo domingo**: só Datashow.
  - **Missa das 16h de todo sábado**: só Datashow (é o único setor que opera no sábado). Na aba "Escala de <setor>" dos outros setores, essas missas fixas sem função do setor ficam escondidas, até pra coordenação; eventos extras continuam aparecendo pra cada coordenação acrescentar as funções dela.
  - Não cria missa em data que já passou. Os dias vêm de `CalendarioService.diasDaSemanaDoMes` (java.time no fuso `America/Sao_Paulo`).
  - **`Evento.versaoFuncoesPadrao`** controla o modelo de funções: missa nova já nasce na versão atual (`VERSAO_FUNCOES_PADRAO`); missa futura numa versão menor (ou `null`, as antigas) é atualizada **uma vez só** (`atualizarModeloDeFuncoes`: tira a "Transmissão" única do modelo antigo se estiver vaga e acrescenta as funções que faltam). Depois disso a geração não mexe mais nas funções daquele evento, pra não desfazer o que a coordenação editou. **Ao mudar `MISSAS_AUTOMATICAS`, suba `VERSAO_FUNCOES_PADRAO`**, senão os eventos já gerados não recebem o modelo novo.
  - **Editar funções**: `PATCH /api/eventos/{id}/slots/{slotId} {rotulo}` renomeia e `DELETE /api/eventos/{id}/slots/{slotId}` remove (`EventoService.exigirPodeEditarFuncao`): Coordenador Geral mexe em qualquer função; coordenador de setor só nas do próprio setor (funções gerais, sem setor, só o Geral). Adicionar continua por `POST /api/eventos/{id}/slots`. No front, os ícones de renomear/remover aparecem ao lado da função pra quem pode (`podeEditarFuncao`).
  - `POST /api/eventos/gerar-escalas-mes` continua existindo pro Coordenador Geral.
- **Escala completa** (`EscalaController`, qualquer usuário autenticado): `GET /api/escalas/domingos?mes=AAAA-MM`, `GET /api/escalas/completa?mes=` (todos os eventos do mês com funções agrupadas por setor, `EscalaCompletaDTO`) e `GET /api/escalas/completa/pdf?mes=` (PDF gerado por `EscalaPdfService` com OpenPDF, no formato de grade da escala impressa da Pascom: A4 paisagem, cada linha é uma função de um setor — o nome do setor ocupa a altura das funções dele —, cada coluna é uma celebração do mês, e a célula traz os dois primeiros nomes de quem serve, "Livre" em amarelo pra vaga aberta e azul claro quando a função não acontece naquele dia; evento grande tem cabeçalho dourado, e o rodapé tem vagas por celebração + o recado fixo de chegar 1h antes. Acima de 9 celebrações no mês a grade é quebrada em mais de uma). Os dois aceitam `?setor=X` pra virar a escala só daquele setor (funções do setor + funções gerais; eventos sem nenhuma delas ficam de fora). No front, a aba Escalas tem "Escala de <setor>" (só funções do `currentSetor` + gerais, eventos de hoje em diante, com barra de mês + "Baixar PDF de <setor>") e "Escala completa" (navegação por mês + "Baixar PDF (todos os setores)" e "Só <setor>").

### Lixeira (exclusão suave)

`Cartao`, `Ideia` e `Evento` usam **exclusão suave**: excluir nunca apaga a linha do banco, só preenche `excluidoEm`/`motivoExclusao`/`detalheExclusao` (enum `MotivoExclusao`: `NAO_DEU_TEMPO`, `JA_PASSOU`, `DUPLICADO`, `MUDANCA_DE_PLANOS`, `NAO_APROVADO`, `OUTRO`). Todo listing normal (`listarTodos`/`listarPorSetor` nos três services) filtra `excluidoEmIsNull`; a lixeira usa as queries complementares (`...ExcluidoEmIsNotNull...`). Endpoints, iguais nos três controllers: `POST /{id}/lixeira` (body `{motivo, detalhe}`, via `ExclusaoRequestDTO`) move pra lixeira, `POST /{id}/restaurar` traz de volta, `GET /lixeira` lista os excluídos (`?setor=X` pra Cartão/Ideia — `Evento` não é filtrado por setor, ver acima). Restaurar/excluir `Evento` exige `temPoderesDeCoordenadorGeral()` (mesma regra de `criar`); Cartão e Ideia continuam sem checagem de papel, igual o resto do fluxo desses dois agregados.

No front, a aba **Lixeira** (`viewLixeira()`) é sector-scoped (Cartões/Ideias do `currentSetor`) mas sempre mostra todas as Escalas excluídas (já que `Evento` é global). Excluir qualquer um dos três tipos abre um modal (`abrirExclusao`/`motivoExclusaoModal`) pedindo o motivo antes de confirmar — não existe mais exclusão direta sem motivo. **Cuidado ao mexer em `EventoService.gerarEscalasDominicaisDoMes`**: o check de duplicidade usa `existsByDataAndTituloAndExcluidoEmIsNull` (não `existsByDataAndTitulo`) de propósito, senão um domingo cujo evento foi pra lixeira nunca seria regerado automaticamente no mês seguinte.

### Integração com Instagram

**Validada de ponta a ponta com a conta real do santuário** (`@santuariodefatima`) via `InstagramService`/`InstagramController`. Usa o fluxo **"Instagram API with Instagram Login"** (Business Login for Instagram) — não exige Página do Facebook vinculada, só que a conta seja Business/Creator. O app Meta é o "Pascom Fátima - Integração" (App ID `1858551365508382`).
- `ContaInstagram` guarda a conexão (id fixo `1L`, uma linha só — é a conta única do santuário). O `accessToken` é sempre criptografado (`CriptografiaService`, AES-GCM com chave em `api.security.instagram.chave` / env var `INSTAGRAM_TOKEN_KEY`) antes de ir pro banco, e nunca é exposto pela API (`@JsonIgnore`).
- `POST /api/instagram/conectar` / `DELETE /api/instagram/desconectar` — só `COORDENADOR_GERAL`. Hoje o token é colado manualmente (gerado em Meta for Developers → Casos de uso → "Configuração da API com login do Instagram" → "Gerar tokens de acesso", exige a conta estar cadastrada como "Testador do Instagram" em Funções do app e aceitar o convite); quando o fluxo OAuth completo for implementado, isso passa a vir automaticamente do callback.
- **Importante**: os tokens desse fluxo começam com `IGAA` e só funcionam contra o host **`graph.instagram.com`** (não `graph.facebook.com`, que devolve "Cannot parse access token" pra esse tipo de token). Isso já está correto em `InstagramService.GRAPH_BASE_URL`.
- **Leitura 100% automática, sem vínculo manual**: o app não precisa mais ligar um `Cartao` a um post. `InstagramService.sincronizarPosts()` lê **todos** os posts da conta (paginado, até `MAX_PAGINAS_SYNC = 10` páginas de 50, ~500 posts) e grava/atualiza uma `PostagemInstagram` por post; roda sozinho a cada 6h (`@Scheduled(cron = "0 0 */6 * * *")`) e também sob demanda via `POST /api/instagram/sincronizar` (só coordenação, no máximo 1 vez a cada 30 min — `ContaInstagram.ultimaSincronizacaoEm` — e nunca duas ao mesmo tempo, já que cada uma faz centenas de chamadas à Graph API). Cada sincronização grava uma nova linha em `MetricaInstagram` (tabela de **histórico**, não valor fixo — a Graph API só guarda métricas por 90 dias, então o histórico de longo prazo depende do nosso banco), com `likes`, `comments`, `saved`, `shares` e `reach` (`GET /{media-id}/insights`).
- **Dashboard**: `GET /api/instagram/resumo?periodo=SEMANAL|MENSAL|ANUAL` devolve o resumo do período (janela de 7/30/365 dias) com os posts e suas métricas mais recentes.
- **Metas de crescimento** (`MetaInstagram`, `GET/POST /api/instagram/metas`, `DELETE /api/instagram/metas/{id}`): `TipoMetaInstagram` = `CURTIDAS_MEDIA`, `ALCANCE_MENSAL`, `POSTS_POR_SEMANA`, `ENGAJAMENTO_MEDIO`; o progresso é calculado ao vivo por `InstagramService.calcularValorAtual`. O assistente de IA tem a ferramenta `analisar_instagram`, que lê o resumo mensal + as metas pra sugerir estratégias.
- **Legado**: `Cartao.instagramMediaId`/`instagramPermalink` são sobra da abordagem antiga de vínculo manual (o endpoint `PATCH /api/cartoes/{id}/instagram` e a coleta por cartão foram removidos) — nada mais escreve nesses campos; só continuam existindo na entidade e no `CartaoResponseDTO`.

### Assistente de IA (chat)

Aba "Assistente" no front (`viewAssistente`/`chatLog` em `index.html`) — um chat com design próprio (bolhas, indicador de "digitando", sugestões, ações executadas destacadas) que conversa em português e **executa ações reais** no sistema via `POST /api/agente/mensagem` (`AgenteController` → `AgenteService`).

- `AgenteService` usa o **Gemini** (`gemini-3.6-flash`, chamado via `RestClient` cru — sem SDK) com **function calling**: manda o histórico da conversa + a lista de "ferramentas" (`ferramentas()`), e fica em loop (até `MAX_RODADAS_FERRAMENTA = 6`) enquanto o modelo pedir pra chamar alguma; quando ele responde só texto (sem `functionCall`), a conversa termina e isso vira a resposta final.
- Ferramentas disponíveis: `criar_evento` (só funciona se quem está no chat for `COORDENADOR_GERAL` — mesma regra do `EventoService.criar`; se der erro de permissão, o próprio prompt do sistema instrui o modelo a explicar com gentileza e não insistir), `criar_ideia` (qualquer um, sempre no `Setor` que o front está mostrando no momento — ver "Navegação por setor"), `listar_eventos` e `listar_ideias` (pro modelo conferir o que já existe antes de criar coisas novas, evitando duplicar — ex.: ao pedir "adicione os santos de outubro", o modelo usa o próprio conhecimento do calendário litúrgico católico pra escolher as datas e chama `criar_evento` uma vez por data).
- Além dessas, `analisar_instagram` (lê `InstagramService.obterResumo("MENSAL")` + as metas) alimenta a análise de estratégia de crescimento do perfil.
- **Quirk do Gemini 3.x**: ao devolver um `functionCall` no histórico da rodada seguinte, é preciso reenviar a `part` **inteira** (com o `thoughtSignature` que veio junto), senão a API responde `400 INVALID_ARGUMENT`. `AgenteService.extrairParteComFunctionCall` preserva isso. O plano gratuito da API é ~5 requisições/min **compartilhadas pelo app todo** (uma chave só); `429` vira uma mensagem amigável pedindo pra esperar.
- Cada chamada de ferramenta é executada de verdade contra os services existentes (não é simulação) e respeita as mesmas regras de negócio/permissão dos endpoints normais — erros (`IllegalStateException`/`IllegalArgumentException`) viram uma `functionResponse` de erro que o modelo recebe de volta e pode explicar ao usuário.
- Configuração: chave em `api.gemini.chave` / env var `GEMINI_API_KEY` (gerada em aistudio.google.com/apikey). Sem chave configurada, o endpoint devolve `IllegalStateException` com mensagem amigável em vez de tentar chamar a API.
- O front manda o `Setor` atual (`currentSetor`) em toda mensagem (`AgenteMensagemDTO.setor`), pra `criar_ideia` e o prompt do sistema saberem em qual "espaço" a conversa está acontecendo.

### Persistência

Por padrão (sem profile ativo, uso local/dev), banco H2 baseado em arquivo em `./data/pascomdb` (ignorado pelo git) com `ddl-auto: update` — o schema evolui automaticamente a partir das entidades, sem Flyway (`spring.flyway.enabled: false` nesse perfil). O SQL é logado (`show-sql: true`).

### Deploy / produção

Existe um profile `prod` em [application.yml](src/main/resources/application.yml) (ativado com a env var `SPRING_PROFILES_ACTIVE=prod`) que troca o H2 por Postgres de verdade, lendo `PGHOST`/`PGPORT`/`PGDATABASE`/`PGUSER`/`PGPASSWORD` — o padrão de variáveis que provedores como Railway já injetam automaticamente ao conectar um banco Postgres ao serviço — e desliga o console do H2. Em produção, defina também `ADMIN_EMAILS`, `JWT_SECRET`, `INSTAGRAM_TOKEN_KEY`, `RESEND_API_KEY`, `APP_BASE_URL`, `GOOGLE_CLIENT_ID` e `GEMINI_API_KEY` (os defaults no `application.yml` são só pra dev local). `server.port` lê a env var `PORT` quando presente (padrão que a maioria dos PaaS usa), com fallback pra `8080`.

Hospedado no **Railway** (projeto `overflowing-empathy`, serviço `pascom-api-gestao-projetos`). A integração automática Railway↔GitHub está **quebrada** (o GitHub App foi desinstalado da conta em algum momento; "Auto deploy unavailable" / "Could not load branches" nas configurações do serviço) — por enquanto o deploy é sempre manual via **Railway CLI** direto da máquina local:
```bash
railway up --ci --message "descrição do que mudou"
```
(`railway login` uma vez, `railway link` já feito na pasta do projeto).

**Deploy com gente usando**: o healthcheck fica **nas configurações do serviço no painel do Railway** (Settings → Deploy → Healthcheck Path = `/api/versao`, timeout 300s; Restart Policy = On Failure), então o Railway só troca o tráfego pra versão nova quando ela já respondeu — sem o 502 de alguns segundos que acontecia antes. Não existe mais `railway.toml` (o formato "Config as Code" foi descontinuado pelo Railway em 2026-12-01). **Não use `railway config migrate --apply`/`railway config apply`**: o IaC novo (`.railway/railway.ts`) assume que tudo do serviço está declarado no arquivo, e o `plan` mostrou que apagaria as 15 variáveis (JWT_SECRET, PG*, chaves) — segredo não vai pro código. A página que já estava aberta continua com o front antigo; por isso `GET /api/versao` (público, horário do build vindo do `build-info` do `spring-boot-maven-plugin`) é consultado pelo front a cada 2 min e ao voltar pra aba, e quando muda aparece o aviso "Saiu uma atualização do sistema — Atualizar agora" (`#updateBanner`, não recarrega à força pra ninguém perder o que estava digitando). Os arquivos estáticos saem com `Cache-Control: no-cache` (`spring.web.resources.cache.cachecontrol.no-cache`), então recarregar sempre traz o front novo. Mudanças de schema devem continuar sendo **aditivas** (coluna/tabela nova, nullable) enquanto a versão antiga e a nova podem rodar juntas por alguns segundos durante a troca. Isso builda com Maven dentro do Railway e sobe uma imagem nova — não depende do GitHub, mas ainda assim vale sempre dar `git push` pra manter o repositório em dia.

**Cuidado com renomear valores de enum que já têm dados em produção**: o Postgres do Railway tem `CHECK CONSTRAINT`s gerados pelo Hibernate a partir dos enums Java (ex.: `tb_usuarios_role_check`), e `ddl-auto: update` **não** atualiza essas constraints sozinho quando um enum muda — elas continuam com os valores antigos e todo INSERT/UPDATE com um valor novo quebra com `violates check constraint`. Isso já aconteceu de verdade nesse projeto; a partir de agora, o jeito certo de corrigir isso é com uma migração do Flyway (ver abaixo), não mais rodando o `ALTER TABLE` manualmente via `psql`.

**Flyway** (só no perfil `prod`, contra o Postgres — o H2 local continua em `ddl-auto:update` puro, sem Flyway, `spring.flyway.enabled: false` no perfil default): adotado numa base que o Hibernate já vinha mantendo sozinho havia meses, então usa `baseline-on-migrate: true` + `baseline-version: "1"` — o Flyway aceita o schema existente como ponto de partida (marca a versão 1 como "já aplicada" sem rodar nada) em vez de tentar recriar tudo do zero. Por isso **não existe `V1__*.sql`** em [src/main/resources/db/migration](src/main/resources/db/migration) — o primeiro arquivo real começa em `V2`. O `ddl-auto` do perfil `prod` segue em `update` por enquanto (as duas coisas convivem: o Flyway roda antes, via `@AutoConfigureBefore(HibernateJpaAutoConfiguration.class)`, e o Hibernate só confirma que não sobrou nada novo pra criar) — a ideia é trocar pra `validate` assim que a primeira migração de verdade (ex.: a próxima troca de nome de enum, usando `ALTER TABLE ... DROP/ADD CONSTRAINT` num arquivo versionado) for confirmada funcionando em produção, momento em que o Flyway passa a ser o dono de verdade do schema. **Versão do Flyway fixada em `11.20.3`** (`flyway.version` no `pom.xml`, mais o módulo `flyway-database-postgresql`): o 9.x que vem com o Boot 3.2 não suporta o PostgreSQL 18 do Railway, e o 12+ removeu `cleanOnValidationError`, que a autoconfiguração do Boot 3.2 chama — com ele a aplicação nem sobe. Só passar do 11.x junto com um upgrade do Spring Boot.

**E-mail transacional (recuperação de senha) usa a API HTTPS do Resend, não SMTP** — confirmado testando com `railway ssh` que o Railway bloqueia as portas de saída 25/465/587 (SMTP), inclusive pra Gmail com senha de app; só HTTPS (443) funciona. `EmailService` chama `api.resend.com/emails` direto via `RestClient` (mesmo padrão de HTTP cru já usado pra Instagram/Google), com a chave em `api.resend.chave` / env var `RESEND_API_KEY` e remetente em `api.resend.remetente` / `RESEND_FROM` (default `onboarding@resend.dev`, funciona sem verificar domínio próprio).

### Convenção de tratamento de erros

Violações de regra de negócio devem lançar `IllegalStateException` (transição de estado inválida, permissão negada) ou `IllegalArgumentException` (entidade não encontrada, input inválido) a partir dos services — ambas são capturadas centralmente pelo `ApiExceptionHandler` e retornadas como `400` com `{"erro": "..."}`. Falhas de Bean Validation em DTOs `@Valid @RequestBody` são capturadas separadamente e retornadas como `{"erros": {campo: mensagem}}`.
